# 金蝶浏览器桥接与下单前供需查询核查

记录时间：2026-10-16 09:46（Asia/Shanghai）  
来源活动日期：2026-10-16

## 这次要解决什么

用户希望 Codex 通过浏览器桥接查看金蝶，不需要学习文员式的图形界面操作，只需要用业务逻辑决定让 Codex 检查什么、改什么。本次任务是把现有浏览器桥接底座优化成 Edge 和 Chrome 都能用，连接金蝶只读检查“零部件下单前查库存、生产、用料”是否已有功能，并把结果记入日志和工具目录。

## 做了什么

### 1. 做了 Edge / Chrome 共用桥接版

从现有 GcWebAuto 项目中抽取通用 CDP 连接和测试，整理成新的独立工程：

- 本地目录：AgentBrowserBridge-CrossBrowser。
- GitHub 私有仓库：[linxi27667/agent-browser-bridge](https://github.com/linxi27667/agent-browser-bridge)。
- 原公司仓库历史、招聘和业务专用代码、运行资料与登录态没有推入新仓库。
- Edge、Chrome 都通过本地 127.0.0.1 调试端口连接。每个浏览器使用独立配置目录；连接前检查浏览器类型、端口、配置目录和代理设置。启动器会阻止使用 Edge/Chrome 日常配置目录。
- 登录/验证码默认由用户完成；调用方项目明确授权并规定本地凭据流程时，可以按该项目规则使用。密码和浏览器登录资料不进入 Git、日志或终端输出。
- Firefox、Safari 不属于这套 CDP 桥接支持范围；它们需要单独的 Playwright 或 WebDriver 连接器。

本机只安装了 Edge，没有安装 Chrome。因此本次完成了 Edge 实际连接验收，Chrome 通过自动化身份校验测试覆盖，但没有实机验收。

### 2. 桥接 Edge 并只读查看金蝶

本机启动 Edge 专用窗口，使用独立 profile 和端口 9224；桥接验证确认浏览器是 Edge，监听仅绑定本机地址。登录按 KingdeeK3CloudOps 既有的本机配置流程临时完成，没有在笔记中记录账号密码。

当前页面显示的数据中心为 GC202508，组织为“101 广州高昌”。本次只检查菜单和打开查询页面，没有新增、修改、提交或审核金蝶业务单据。

金蝶菜单中确认存在以下功能：

- 库存预留关系查询：在“生产制造 → 计划管理 → 报表分析”和“供应链 → 库存管理 → 报表分析”各有一个菜单入口。
- MRP订单供需查询。
- 物料供需汇总表、物料供需明细表。
- MRP运算结果汇总表、明细表。
- 即时库存明细。
- 生产订单列表、生产用料清单列表。

这说明系统里已经有查库存、查生产供需和查用料相关的基础功能，后续不应先假设需要从头开发。

### 3. 检查了物料供需明细表

打开“物料供需明细表”后，看到过滤条件包括“物料范围、计划方案、运算编码”，结果区显示 0 行。本次没有设置过滤条件，也没有执行查询。

这表明该报表与计划方案、MRP 运算结果有关；它是否能直接回答刘博下单前的即时判断，还需要拿一个真实零部件核对数据来源、供给日期、预留和缺料口径。菜单存在不等于业务配置已经正确，也不等于一个报表已经把判断所需信息合在一起。

## 当前判断

用户最初提的“下单前看库存、生产、用料”，金蝶里已有相关查询菜单。下一步应先用一个真实的非按单生产零部件，检查现有查询是否能同时回答：

1. 现在有多少库存真正可用，是否被预留、待检或占用。
2. 已安排生产多少、还差多少、预计何时入库。
3. 这个零部件的有效需求来自哪些订单或用料清单，什么时候需要。
4. 需求日期前仍有多少缺口，数据能否回到来源单据。

若现有报表能提供正确数据，优先把入口、过滤条件和字段整理方便；只有确认必须反复跨页、而且现有报表不能补齐时，才开发一个“下单前看一眼”的汇总页。该页应能点回库存、生产或用料来源，不要直接自动下生产单。

## 10:34 · 结合真实工单形成生产前检查方案

后续继续只读核对了 31270880“油缸垫片”的物料供需状态。工单 MO020578 数量 400，系统列为生产供应，但它的计划完成日期为 2026-09-28，状态仍为“下达、未领料”，查询日期已是 2026-10-16。因此这 400 件必须先找生产确认，不能直接当作可靠到货，也不能因为账面库存为 0 就重复下单 400 件。展开的下层物料 35010003“Q235热轧开平普板T3”显示需求 185.09 kg、账面库存 854.8 kg、已分配 185.09 kg、预计结存 669.71 kg。

结合 10 月 12 日的 26GC106 整机订单与 MO020624 控制盒工单，方案把检查拆成两件事：一是这个零部件本身的库存、占用、需求、在产和到货时间；二是为本次计划生产所需的 BOM 材料能否按时到位。账面不足只标“待核候选”；逾期无领料/报工的工单标“待生产确认”；按单件走销售订单链路，不混入通用件备货判断。检查页只给依据和来源，不替计划员创建或审核工单。

完整实施方案（含流程、数量口径、异常分工、三组真实样本和验收办法）：[非按单零部件生产前检查方案](../../../KingdeeK3CloudOps/docs/plans/2026-10-16-non-mto-preproduction-check.md)。本次没有修改金蝶配置、MRP、库存或生产单。

## 10:56 · 暂定采用生产前检查方案

用户暂定采用“先复用金蝶现有查询、先做只读核对；确认多处信息仍需人工拼接后，再开发只读汇总入口”的方案。

方案重点：金蝶已有库存/供需、预留、生产订单和生产用料等查询，不从头重做；后续要让计划人员能围绕一张待安排的计划单，一次看清零件库存和已有供给、生产所需材料及异常提示，并能回查数字来源。逾期未动的工单和账面材料不足都先提示人工核实；不自动下生产单或修改业务数据。

这只是暂定方案方向，尚未开始开发或改动金蝶。后续先选广州高昌一项当前有效的非按单零件做只读试点，再根据核对结果决定是否需要开发汇总页。
