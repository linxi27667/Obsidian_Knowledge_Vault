# 高总会议纪要与数字化优化推理

## 结论先看

高总把当前工作的起点收窄到**焊接生产**：先弄清每天计划做什么、实际完成多少、积压多少、完成量对应多少标准工时，再逐步追下料、激光切割和机加如何衔接。近期先研究未来 1–3 天能否相对稳定安排，同时看第 4–6 天要准备什么。冻结范围、例外和谁能改计划尚未形成规则。

会议没有决定重做金蝶、开发完整客户端或上线自动操作金蝶的 Agent。先查金蝶已有“工序计划”“工序汇报”等页面、过滤方案和字段，再判断需要报表、MES 还是小工具补什么。

对库存和领料问题，高总特别提醒：只增加备料员不能保证领料正确，关键是有无清楚规则、实际数量确认和责任记录。数字化也不是消灭所有生产偏差，而是把偏差量化成能看见、能分析的指标。

## 2. 高总表达的方向

### 先看焊接，不要一口气铺开全厂

高总希望了解焊接每天完成多少标准工时、积压多少工序、任务是过多还是不足。他提出近期尝试稳定未来三天，并继续查看第 4–6 天需要准备什么。转写表达了“尽量不动/固定”的意思，但**冻结规则、例外、调整权限和记录方式都需要 PMC 与车间确认**。

他认为下料、激光切割和机加目前难以按日明确准备什么，可能在下游催促后临时调整，并提出前道供给跟不上焊接需求的判断。这是管理层提出的待验证问题，尚不能说数据已经证明焊接是全厂唯一瓶颈。

### 把计划和实际量出来

高总建议比较每天早上的计划和当天实际完成情况，逐步找出偏差。他强调生产管理不是保证问题永远消失，而是把过多、过少、过早、过晚量化，成为车间管理能够使用的指标。焊接积压量、每日完成量和标准工时是会议提到的候选信息；指标口径、确认人和是否用于绩效尚未定稿。

### 先查现有系统

刘博说金蝶“工序计划”可查看焊接工单，“工序汇报”可查看每日汇报量。高总要求先看过滤方案、字段，再逐步确定要提取的信息。先检查金蝶和 MES 已有页面、报表及数据，再判断缺口。不能仅因页面暂时没看到，就断言系统没有功能。

### 领料问题先核实规则

我汇报了工人取料可能未及时登记、账面与现场数量可能不符、缺料会导致加急和等待等线索。高总指出，单纯增加备料员也可能仍然乱拿，关键是规则和执行。因此后续要查具体物料、工单、拿料与登记步骤、确认责任及造成的影响；不能先把根因定成“缺备料员”。这没有否认库存差异可能导致停工，而是要求用事实把因果链查清。

### 本周列出 3–5 项候选工作

高总希望我和刘博结合现有生产流程和系统，列出至少 3–5 项可由 AI 或技术简化的工作，说明本周打算做什么，再一起定优先级。他举例询问工单能否减少找图纸的重复动作，刘博答复目前仍需图纸。会议结束时没有批准具体项目；下方是供讨论的候选清单。

## 3. 与此前问题分析的关系

此前刘博流程说明、余总/PMC 交流及订单样本提供了领料记录、库存账实、采购周期、齐套、工序排程和系统同步等待核线索。高总本次给了优先顺序：先看焊接计划和实际，再向前追下料、激光切割、机加的准备节奏。

- 库存与领料是重要线索，需用真实订单、料位和领退料记录确认影响范围。
- 焊接是本次会议指定的观察起点，但积压和产能仍需当前工单与报工验证。
- 前道准备不足是管理层提出的判断，需要核对前道任务、交接时间和焊接待料事实。
- 金蝶、MES 和辅助工具是记录分析手段，不能替代现场规则、人员确认和盘点。

26GC106 是历史订单样本；MO020624 是控制盒部件单的局部跟踪。它们适合学习系统关系，不应未经 PMC 确认就当成当前试点或当前缺料证据。

## 4. 本周 5 项讨论候选

以下尚未批准或实施：

1. **盘点现有页面。** 和刘博查看“工序计划”“工序汇报”、过滤方案、字段、权限和数据更新时间，并确认 MES 是否也记录这些数据。
2. **选少量有效工单做基线。** 请 PMC 选 3–5 张当前焊接工单，记录工序、计划数量/日期、标准工时、当日汇报量、剩余量和积压时间，不直接拿历史订单代替。
3. **统一计划与实际口径。** 确认计划量、实际完成量、合格量、标准工时和积压分别来自哪里、谁确认、何时更新；没有质量记录就标为缺项，不估算。
4. **讨论短期计划规则。** 与 PMC、车间确认 1–3 天安排的稳定范围、第 4–6 天预告方式、改计划权限、插单/缺料处理和原因记录。
5. **找一项能减轻刘博重复工作的事。** 梳理查工单、找图纸、汇总进度等重复步骤，判断已有报表、字段关联或辅助工具能否省时；先做只读展示/流程试稿再评估开发。

## 5. 焊接看板需要核实的数据

| 数据 | 要确认的事情 | 建议确认人 |
|---|---|---|
| 当前有效工单、优先级、批准计划 | 排除已完结或已变更的单据 | PMC、生产主管 |
| 工序计划/工序汇报入口、过滤和字段 | 确认现有金蝶能力 | 刘博、金蝶管理员 |
| MES 报工及同步时间 | 确认在哪个系统产生、是否及时回写 | MES 负责人、刘博 |
| 标准工时、工序/工作中心定义 | 避免把件数误当产能 | 工艺、生产主管、PMC |
| 完成量、合格量、返工量 | 区分完成和合格；没有记录则标缺项 | 车间、质量 |
| 积压按数量、工时还是等待天数计算 | 让“积压多不多”有稳定口径 | 高总、生产主管 |
| 插单、停工待料、计划变更及批准人 | 解释计划和实际的差异 | PMC、车间主管 |
| 前道向焊接交付时间、缺件记录 | 验证上游节奏是否造成等待 | 前道与焊接主管 |
| 页面、报表或 API 权限 | 确认数据可读范围与技术条件 | 系统管理员 |

金蝶 Open API 或 K3CloudOps 能读到哪些表单和字段，需按公司版本、权限和配置逐项核实。会议展示了 API 和项目，不等于所有数据都开放或可以绕过权限。

## 6. 试点的衡量方式

先拿到可回查的日常基线，再讨论改善。候选指标包括：计划与实际标准工时差异、未完成工单数量/剩余工时/等待时间、计划变更次数及原因、焊接待料暂停的次数与时长、报工相对现场实际的延迟或漏记；若已有质量数据，再看合格和返工。

定义和来源应先由管理人员确认。没有可靠口径和基线前，不承诺改善比例，也不直接用于个人绩效。

## 7. 技术边界

高总介绍了公司金蝶服务器/数据库、MES、银企直连、金蝶 Open API 和 K3CloudOps。部分架构名称在转写里听不清；银企直连是银行集成，和焊接优化分开。

可先使用授权范围内的金蝶页面、报表、MES 数据和 API 探查，再决定是否补工具。**会议没有证明 Open API 覆盖所有金蝶数据，也没有证明 GitHub 项目含金蝶客户端或产品源码。**正式写入、审核或改计划需有明确授权、规则和业务人员确认。
