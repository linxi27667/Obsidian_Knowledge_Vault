# Gc_Iot_Lift 系统与代码架构（四套固件，一条管理链路）

## 核心概念

- ==系统边界==：STM32 负责设备安全与动作，TAS DTU 负责联网，Web 负责管理。
- ==固件分层==：Core/HAL → BSP → APP → Driver/Task。
- ==变化点==：产品状态机和 IO 映射；==稳定点==：RTOS、DTU、MQTT、存储和管理协议。

## 一、总体架构

```text
按钮/急停/限位/光电
        ↓
  STM32F407 + FreeRTOS
   ├─ Lift 控制任务
   └─ TasDtu 通信任务
        ↓ GPIO                ↕ USART3 DMA/FIFO
  继电器/电机/气阀/电磁铁    TAS-LTE-892D_s4
                                    ↕ 4G MQTT
                              Broker 8.134.167.240
                                    ↕
                              Node.js 管理平台
                                    ↕
                              浏览器
```

```text
Gc_Iot_Lift/
├─ GC_Big_Scissor/      # 大剪 product_type=3
├─ GC_Small_Scissor/    # 小剪 product_type=1
├─ GC_Thin_Scissor/     # 超薄 product_type=2
├─ GC-Two_Pillars/      # 两柱 product_type=0
├─ Gaochang_Iot_Web/    # Node.js 管理平台
├─ 接线文档.docx
└─ 所有控制逻辑.md
```

每个固件工程内：

| 层级 | 目录 | 主要职责 |
|---|---|---|
| 芯片初始化 | `Core/` | `main()`、时钟、GPIO、DMA、UART、SPI、FreeRTOS |
| 厂商库 | `Drivers/` | HAL、CMSIS |
| 中间件 | `Middlewares/` | FreeRTOS、FIFO |
| 板级层 | `BSP/` | UART DMA/FIFO、SPI、W25Qxx 底层 |
| 应用层 | `APP/` | 状态机、安全、IO 映射、IoT JSON、存储和日志 |
| 任务封装 | `Driver/` | `Lift_Task`、`TasDtu_Task`（非官方 Drivers） |
| 工具与工程 | `MDK-ARM/` | Keil 构建、J-Link 烧录 |

> [!NOTE]
> `Driver/` 是任务/业务门面，不要和 STM32 官方 `Drivers/` 混淆。

## 四、公共框架与产品插件

大剪、超薄和两柱使用 `lift_ops_t`：

```c
typedef struct {
    void (*init)(void);
    void (*on_estop)(void);
    void (*on_photoelectric_blocked)(void);
    void (*on_clear_alarm)(void);
    void (*poll)(void);
} lift_ops_t;
```

公共 `lift_core` 先处理安全，再调用当前产品的 `ops->poll()`。

小剪是特殊版本，核心在 `app_lift_core.c`：

```text
采集 → 前置安全 → 状态转换 → 输出仲裁 → 最终安全闸门 → 硬件输出
```

## 六、四套工程的复用现实

当前仓库不是一个编译时选择四机型的单工程，而是四个独立固件目录。优点是交付和烧录简单；缺点是公共修复需要同步到多份工程，容易产生漂移。

答辩可诚实表达：

> 我们通过统一接口和目录规范实现逻辑复用，但当前物理仓库仍是四份独立固件工程。后续可以进一步抽取公共组件，减少多工程同步成本。

## 七、架构边界

- Web 下发的是管理命令，不直接操纵 GPIO。
- `app_tas_dtu.c` 负责协议，不应实现产品动作时序。
- 产品状态机通过 `App_IO_Write()` 输出，不直接散落调用 HAL GPIO。
- ISR 只搬运数据和更新缓冲，JSON 解析放在任务上下文。
- W25Qxx 写入不能破坏控制任务实时性。
