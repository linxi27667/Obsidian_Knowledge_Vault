## 2. 项目是什么（融合作品说明书摘要）

### 2.1 30 秒版

> 面向三层建筑模型的智能中控。P4 做人机交互、语音 AI、本地人脸与规则决策；板载 C6 提供 Wi‑Fi；三台 S3 做楼层执行与传感。  
> 主线是 **AI 语音 + MCP 语义 + MQTT 设备通信**，形成“理解 → 决策 → 执行 → 回显”闭环。

### 2.2 作品说明书七大功能（答辩安全口径）

| 说明书功能 | 你怎么说 |
|---|---|
| AI 语音交互 | 离线唤醒 + 云端 ASR/LLM/TTS；意图可变成多设备动作 |
| MCP 设备控制 | 大模型只能调已注册工具；P4 再校验、再下发 |
| 多楼层分布式 IoT | P4 决策，S3×3 执行；MQTT 下发/回传 |
| 环境传感报警 | 三楼火焰/雨滴 ADC；超阈值确认后联动 |
| 自动场景 | 火警、雨天、回家、睡眠等主机编排 |
| 触屏可视化 | LVGL 七页：总览/控制/灯光/场景/环境/网络/设置 |
| 人脸识别 | P4 本地识别，可联动回家场景 |

### 2.3 说明书四条创新点（可验证说法）

1. **语义级控制**：自然语言 → MCP 工具 → 设备协议，不是模型直接瞎写 GPIO。  
2. **分布式二进制 MQTT**：单播/广播/心跳快照，嵌入式侧比 JSON 更省、更确定。  
3. **传感本地闭环**：感知 → 规则 → 执行，安全路径不绑死云端。  
4. **Flag-Driven 从机**：回调改标志，任务刷硬件，通信与执行解耦。

### 2.4 应用领域（说明书原文方向，点到即可）

智能家居/多层中控、宿舍管理、大棚环境监测架构复用、IoT 网关原型。

## 4. 楼层设备与传感器（说明书 + 代码）

| 楼层 | 设备 | 答辩要点 |
|---|---|---|
| 1F | 大厅灯、大门舵机、总闸 | 门：协议舵机 index **6**，开180/关0 |
| 2F | 多路灯、风扇继电器、晾衣杆、WS2812 | 心跳可 V3（含 RGB）；衣杆 index **8** |
| 3F | 阳台灯、左右天窗、晾衣杆、火焰/雨滴 | 天窗角度不对称；**smoke_mv=火焰 mV** |

**传感器类型标准答：**

> 三楼火焰、雨滴都是**模拟量传感器**，S3 用 **ADC** 采电压。  
> 连续多次超阈值才报警。  
> 协议里 `smoke_mv` 是历史兼容字段名，**实际装的是火焰电压，不是烟雾**。  
> 另外中控摄像头是数字图像传感器，做人脸，不是环境烟雾传感。

### 5.2 ESP32 怎么连 Wi‑Fi？（你说“我不会”时的标准答案）

分两种板：

#### A. 普通 ESP32-S3（从机）——经典流程

```text
1. 初始化 NVS（存 SSID/密码）
2. 初始化网卡协议栈（LwIP）与 Wi‑Fi 驱动
3. 设为 Station 模式（做客户端，不是路由器）
4. 配置要连的 SSID/密码
5. 启动连接，等 GOT_IP 事件
6. 拿到 IP 后，才能连 MQTT Broker
```

**答辩白话：**

> S3 芯片自带 Wi‑Fi。程序里把芯片设成手机那种“连热点”的 Station 模式，写入路由器账号密码，连上后获取 IP，再作为 MQTT 客户端连 Broker，收命令、发心跳。

#### B. ESP32-P4 中控——多一步协处理

```text
P4 无 Wi‑Fi 射频
  → 板载 C6 负责真正发射/接收 Wi‑Fi
  → P4 与 C6 用 SDIO 相连
  → ESP-Hosted 把 C6 虚拟成 P4 的网卡
  → 上层仍调用 WifiManager / 标准网络 API
  → StartNetwork() → 读已存 SSID → StartStation()
  → 连上后 NetworkEvent::Connected
  → 再启动小智云协议 + 智能家居 MQTT
```

**金句：**

> 对应用层来说“还是连 Wi‑Fi”，但射频在 C6，P4 通过 SDIO + ESP-Hosted 使用它。这是官方典型方案，不是野路子。

**配网：**

> 若 NVS 里没有 Wi‑Fi 账号，会进配网模式（如热点配网/配置界面）；BOOT 键在启动阶段也可进配网。账号保存在 NVS，下次上电自动连。

**和“有线网”对比帮助理解：**

| | 有线网卡 | 本项目 P4 |
|---|---|---|
| 谁发无线 | 路由器侧 | C6 |
| CPU 怎么用网卡 | PCIe/USB | SDIO + Hosted |
| 应用 API | socket | 同样是 IP 网络 API |

### 5.3 麦克风 / 喇叭怎么驱动？

```text
声音（模拟）
  → 麦克风
  → ES8311 音频编解码芯片（ADC 录音 / DAC 放音）
  → I2S 数字音频流进 P4
  → AudioService 做缓存、唤醒、编码
  → 上行到云端（对话）或本地播放 TTS/提示音
```

- **I2C**：读写 ES8311 寄存器（音量、采样率、上电等）  
- **I2S**：连续传输 PCM 音频数据  
- 工程采样率：**24 kHz** 输入/输出（板级配置）  
- 代码：`GetAudioCodec()` 返回 `Es8311AudioCodec(...)`，引脚来自板级 BSP（MCLK/SCLK/LCLK/DOUT/DSIN 等）

**唤醒：**

> 本地音频前端（AFE/ESP-SR）在芯片侧检测唤醒词，触发 `WAKE_WORD_DETECTED`，再打开与云端的音频通道。识别整句内容通常在云端 STT。

**被问“是不是麦克风阵列”：**

> 以实装为准：本板核心是 **ES8311 codec 音频链路**。若没有多麦波束成形算法，不要吹麦克风阵列。

### 5.4 摄像头怎么驱动？人脸怎么跑？

```text
SC2336 等图像传感器
  → I2C/SCCB：配置曝光、分辨率等
  → MIPI-CSI：高速差分通道传图像数据（不占普通 GPIO 乱飞线）
  → esp_video / EspVideo 取帧
  → face_recog 任务（P4 core1）
  → ESP-DL 模型做人脸检测/特征比对
  → 结果 Schedule 回主任务 → UI / 回家场景
```

源码注释要点：SCCB 复用已有 I2C 总线（与 ES8311、GT911 共用），图像走 MIPI-CSI。

**答辩白话：**

> 摄像头不是 USB 免驱那么简单。传感器要 I2C 配置，像素数据走 MIPI-CSI 专用接口；我们用乐鑫 esp_video 框架取帧，人脸在 P4 本地用 ESP-DL 推理，数据库在 face_db 分区，**不是把视频丢到云端识别**。

### 5.5 屏幕和触摸怎么驱动？

```text
MIPI-DSI 屏（1024×600）
  → BSP 初始化 DSI + 面板
  → LcdDisplay / LVGL 绘制 UI

GT911 触摸
  → I2C 读触摸点
  → lvgl_port 注册为输入设备
  → 点击事件进页面回调
  → 回调里 mqtt_send_* 控设备
```

**金句：** 屏负责“看见”，触摸负责“点到”，业务仍在我们的 page 回调和设备模型里。

### 5.6 从机灯 / 舵机 / ADC 怎么驱动？

| 设备 | 驱动方式 | 软件路径 |
|---|---|---|
| 普通灯 | GPIO 高低电平 | flags → IotControl_Task → BSP |
| WS2812 | 单线时序（RMT/专用驱动） | 二楼氛围灯 |
| 舵机 | LEDC 输出 PWM | 角度映射占空比；协议 index 6 起 |
| 继电器 | GPIO 驱动线圈 | 风扇等 |
| 火焰/雨滴 | ADC 采样 mV | 500ms 任务 + 阈值 + 连续次数 |

**Flag-Driven（说明书重点，务必会说）：**

> MQTT 回调里**不直接慢慢转舵机**。回调只改 `g_device_flags`，`IotControl_Task` 约 100ms 读标志位再驱动硬件。这样网络回调短、实时更稳。

### 5.7 被问到“底层细节我没背到”时的万能答法

> 这个外设在板级 BSP 初始化，上层通过 Board 抽象获取：`GetAudioCodec()` / `GetCamera()` / `GetDisplay()`。  
> 我掌握的是接口与数据流：例如音频是 I2C+I2S+ES8311，摄像头是 CSI+esp_video，网络是 C6+Hosted。  
> 具体引脚以 `esp-p4-function-ev-board` 与 BSP 头文件为准。

这样显得诚实且有结构，比瞎编寄存器强。

## 6. 主机与从机通信（必问）

### 6.1 一句话

> P4 与 S3 **不点对点直连**，都经 **MQTT Broker 发布订阅**；共享头文件定义二进制包。

### 6.2 两套网络（超高频）

| 通道 | 干什么 | 载荷 |
|---|---|---|
| 小智云 | 聊天、STT/LLM/TTS、MCP | JSON + 音频 |
| 智能家居 MQTT | 控设备、心跳、传感 | **二进制 packed** |

**金句：** 能聊天 ≠ 能开灯。

### 6.3 Topic 速记

- 下：`xiaozhi/iot/cmd/{1|2|3}`、`broadcast`，电源 `power/*`  
- 上：`resp/{mac}`、`heartbeat/{mac}`、`announce/{mac}`、`sensor/{mac}`  
- 心跳约 **30s**，超时约 **60s** 判离线  
- 命令包约 **8 字节**

### 6.4 为什么二进制不是 JSON？

体积小、解析确定、动态内存少；代价是可读性——所以用版本号、长度校验、预留字段、共享头文件。

### 6.5 舵机 index 为什么从 6？

协议逻辑编号：灯/继电从 0，舵机从 6，避免类型混用。本地数组仍 0/1/2，收发包 ±6。

## 7. 怎么和 AI 聊天、AI 怎么控硬件

### 7.1 聊天

```text
唤醒 → 录音(ES8311/I2S) → 小智通道上传
→ 云端 STT → LLM → TTS
→ 屏幕文本 + 喇叭播放
```

Locked（未登录）可忽略唤醒。

### 7.2 控硬件（核心背诵）

```text
“打开二楼客厅灯”
→ LLM 调 MCP：set_light(floor=2,index=1,on=true)
→ P4 ParseMessage / 参数校验
→ Schedule 回主任务
→ mqtt_send_command → cmd/2
→ S3 改 light[1] → 100ms 写 GPIO
→ resp/心跳 → device_model → UI
```

**MCP vs MQTT：**

- MCP：语义（想干什么）  
- MQTT：传输（包发哪）  
- GPIO：物理（电平怎么变）

### 7.3 场景例

- **火警**：开门、开天窗、全灯警示等（主机编排）  
- **雨天**：收衣、关窗、氛围提示；主机可有雨锁强制衣杆关闭  
- **回家/睡眠**：多设备组合

自动模式维护约 **1s** 量级，勿吹未测“毫秒级安全闭环”。

## 8. 软件关键概念（够用即可）

| 概念 | 白话 |
|---|---|
| FreeRTOS 任务 | 并行的“小程序”，如人脸任务、MQTT 任务、从机控制任务 |

## 9. 设计题短答

**为什么 P4 还要三台 S3？**  
中控适合 UI/AI/视觉；楼层适合分布式 IO；线束短、可扩展。

**断网？**  
分公网 / 局域网 / Broker / 节点。断公网丢云端语音；局域网+Broker 在则触控与本地规则仍可；Broker 挂则主从难协同。

**实时性？**  
触控路径较短；语音看云端；安全有采样与确认，按秒级策略描述。

**扩展第四层？**  
复制 S3 工程改 id/Topic；P4 设备表与 UI 加 floor；协议尽量不动。

**不足？**  
公网 Broker 与云依赖、TLS/认证、OTA、本地命令词兜底、事务 ACK——诚实+改进方向。

## 10. 「你也用小智」拷打（必背）

### 60 秒

> 小智解决的是端侧语音 Agent 底座。我们复用它，就像产品基于 Linux，不重复造 STT/LLM/TTS。  
> 我们的交付是全屋控制面：P4/C6/S3 异构、自研设备协议、三套从机、设备模型与中控 UI、本地人脸与火警雨天规则。  
> **小智是对话接口；我们做神经、四肢和本地反射弧。**

### 金句

> 别人证明芯片能聊天；我们证明聊天之后，房子听得懂、做得到、看得到、关得住。

### 禁止

否认用小智；贬低小智；吹“模型是我们的”；只说“加了几个 MCP”。

### 和常见小智 Demo 对比

| 维度 | 常见 | 我们 |
|---|---|---|
| 形态 | 单板 | P4+3×S3 |
| 联网 | 片内 Wi‑Fi | P4 靠 C6+Hosted |
| 设备 | 单板 IO | 二进制协议+场景 |
| 交互 | 多语音 | 语音+触屏+人脸+传感 |
| 智能 | 多靠云 | 云端语义+本地规则/人脸 |

## 13. 错误说法对照

|---|---|
