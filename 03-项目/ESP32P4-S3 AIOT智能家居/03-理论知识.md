# 理论知识（理解项目为什么这样设计）

## 核心概念

- ==分层==让硬件、协议、业务和界面可以独立变化。
- ==事件驱动==让任务在无事件时阻塞，减少 CPU 浪费和线程耦合。
- ==设备模型==是 UI、规则和网络之间的单一事实源。
- ==云端智能、本地自治==在能力、延迟、隐私和可靠性之间取平衡。

## 一、P4 与 S3 分布式架构

P4 擅长显示、摄像头、音频和较大内存任务，但没有无线电；板载 C6 经 ESP-Hosted 提供 Wi-Fi；S3 自带 Wi-Fi，适合靠近设备做 GPIO、PWM、ADC。项目因此采用“中央决策 + 楼层执行”。

| 方案 | 优点 | 代价 |
|---|---|---|
| 全部接 P4 | 软件简单 | 线束长、IO 集中、P4 无原生 Wi-Fi |
| 每层独立 S3 | 分布式、易扩展 | 节点和协议更复杂 |
| 当前 P4+C6+S3 | 多媒体与执行各取所长 | 需要 Broker、心跳和协议兼容 |

## 二、ESP-IDF 组件与板级抽象

ESP-IDF 通过 CMake 组件组织代码。`sdkconfig` 决定目标芯片和板型，`main/CMakeLists.txt` 决定实际编译哪些源文件。

Board 抽象让上层只依赖：

```cpp
Board::GetInstance().GetDisplay();
Board::GetInstance().GetAudioCodec();
Board::GetInstance().GetCamera();
```

当前具体实现由 `DECLARE_BOARD(ESP32P4FunctionEvBoard)` 注册。

## 三、FreeRTOS 并发模型

### 3.1 任务

任务用于长期、可阻塞或周期工作的独立执行流。本项目典型任务：

| 任务 | 作用 |
|---|---|
| Application 主循环 | EventGroup 驱动业务 |
| network_start | 联网 |
| sh_iot_mqtt | MQTT 维护、天气、自动模式 |
| face_recog | 摄像头与人脸 |
| S3 iot_ctrl / mqtt_hb | 设备刷新与心跳 |

### 3.2 EventGroup

EventGroup 用一个位图表示多种事件。`Application::Run()` 阻塞等待任意位：

```cpp
xEventGroupWaitBits(event_group_, ALL_EVENTS,
                    pdTRUE, pdFALSE, portMAX_DELAY);
```

这比持续检查标志位更节能、更可控。

### 3.3 Schedule 与线程边界

网络、摄像头、MCP 回调可能运行在不同任务。`Application::Schedule()` 将闭包放入主任务队列，再置位事件组：

```cpp
{
    std::lock_guard<std::mutex> lock(mutex_);
    main_tasks_.push_back(std::move(callback));
}
xEventGroupSetBits(event_group_, MAIN_EVENT_SCHEDULE);
```

原则：回调尽量短，跨线程状态修改通过消息或调度队列。

## 四、状态机

状态机将“系统处于什么阶段”变成明确状态：

```text
Starting → Locked → Idle → Listening → Speaking
                     ↘ Connecting / WifiConfiguring / Upgrading / Activating
```

状态变化可统一控制麦克风、唤醒词、音频播放、UI 和电源策略。Locked 时忽略唤醒与 ToggleChat。

## 五、发布订阅与 MQTT

MQTT 用 Topic 解耦发布者和订阅者：

- P4 不需要知道 S3 内部驱动。
- S3 不需要知道命令来自语音还是触屏。
- Broker 负责路由。

QoS 0 开销低，适合频繁心跳；QoS 1 至少送达一次，适合命令和响应，但处理应尽可能幂等。

本项目另有“小智云协议”通道，与智能家居设备 MQTT 是两套连接。

## 六、MCP 与工具调用

MCP 将自然语言约束为具名工具和结构化参数：

```text
“打开二楼客厅灯”
→ self.iot.set_light(floor=2, index=1, on=true)
→ P4 参数校验与设备映射
→ MQTT 命令
```

MCP 解决语义层，MQTT 解决传输层，S3 BSP 解决物理层。

## 七、设备模型与事件驱动 UI

如果 MQTT 回调直接修改 LVGL，会产生线程安全、重复解析和页面耦合。项目采用：

```text
MQTT → 协议解析 → device_model → ui_event
→ LVGL 上下文派发 → 页面读取模型并更新
```

准确描述是“事件驱动为主，周期派发为辅”：UI 用 50 ms timer 派发事件，智能家居任务用 1 s tick 维护 MQTT、天气和自动模式。

## 八、二进制协议与版本

`__attribute__((packed))` 防止结构体对齐填充，确保 P4 与 S3 字段偏移一致。

必须：

- 协议版本号（V2/V3）
- 固定字节序
- 长度校验
- 预留字段
- 旧版本兼容

心跳 V2/V3 携带完整状态快照，使 P4 重启或重连后重新收敛真实状态。

### 协议索引 vs 本地索引

舵机协议 index 从 6 起，本地数组从 0 起。这是为了在统一设备空间中给灯/继电器/舵机留出互不冲突的逻辑编号。

## 九、内存、PSRAM 与实时性

| 内存 | 适合内容 |
|---|---|
| 内部 SRAM | 任务栈、DMA 关键数据、低延迟对象 |
| PSRAM | 摄像头帧、图片、UI 大资源、设备模型、模型工作区 |
| Flash | 程序、静态资源、人脸数据库分区 |

实时性不能只看 CPU 主频，还要看任务优先级、阻塞时间、采样周期、MQTT 延迟、1 s 自动模式 tick 和设备刷新周期（S3 100 ms）。

## 十、本地 AI 与云端 AI

| 能力 | 位置 | 原因 |
|---|---|---|
| STT/LLM/TTS | 小智云端 | 模型规模和效果 |
| 人脸识别 | P4 本地 | 隐私、延迟、断公网 |
| 安全规则 | P4 本地 | 不等待云端推理 |
| 设备执行 | S3 本地 | 靠近硬件、稳定刷新 |

> [!WARNING]
> 断公网不等于全部功能可用：语音云端不可用；P4/S3 协作还取决于局域网和 MQTT Broker。
