# 本地录音转写与摘要

这套方法用于把本地中文讨论录音转换成带时间戳的文字稿，再自动抽取原句、整理现状。2026-10-12 已用于余总与 PMC 面试的两段 `.m4a` 录音，合计约 24 分 33 秒。

**用户约定：后续录音优先继续使用这套本机开源方案，复用已有模型和依赖。音频识别与原句抽取交给程序；业务解释、因果分析和建议另行依据文字稿整理。**

## 今天用了哪些开源项目

| 项目或模型 | 今天的实际作用 | 来源 |
|---|---|---|
| sherpa-onnx | 本机运行语音模型的工具框架，调用识别和说话人分析接口 | [项目仓库](https://github.com/k2-fsa/sherpa-onnx) |
| SenseVoice | 主要音频转文字模型，生成正文及用于定位的识别结果 | [项目仓库](https://github.com/QwenAudio/SenseVoice) |
| Paraformer | 第二套中文识别模型，独立识别同一片段，保留对照供核查 | 通过 sherpa-onnx 运行，具体模型见下方位置 |
| PyAV | 解码 `.m4a` 音频，并重采样到 16 kHz 单声道 | 今天脚本中使用 `av` 库 |
| jieba | 将中文句子切成词，供摘要算法判断句子之间的联系 | [项目仓库](https://github.com/fxsjy/jieba)；本次版本 0.42.1 |
| Sumy / TextRank | 按词语联系给句子排序，抽取原句作为重点摘要 | [项目仓库](https://github.com/miso-belica/sumy)；本次 Sumy 版本 0.13.0 |

其中，**真正把声音变成文字的是 SenseVoice 和 Paraformer；sherpa-onnx 负责运行它们。** Sumy 做的是从已有转写中选句，不能独立判断公司现状和管理问题。

## 实际处理顺序

1. 用 PyAV 读取录音，转换为 16 kHz 单声道采样。
2. 大致每 20—28 秒，在较安静的位置切段；识别时加入少量边界重叠，减少断在一句话中间的影响。
3. 用 SenseVoice 识别，程序直接写出完整文字和各段相对时间戳。
4. 用 Paraformer 再识别相同片段，分别保留两套结果，供回查疑似错词。
5. 用 jieba 分词，再由 Sumy TextRank 抽取全篇重点，并按约 2 分钟的区间补充选句。
6. 根据完整文字稿整理业务总结、现状、推断、建议和待确认项。
7. 按日期与独立事项归档。原始稿保留机器识别结果，整理稿解释内容，日志正文能够独立阅读。

今日程序抽取每段录音的全篇重点原句各 18 条，另保留分时段选句。它可以帮助找重点，重要但只出现一次的内容仍可能没被选中，业务总结需要回到全文检查。

## 今天的效果如何

**作为讨论初稿和主题整理工具，可以继续使用；逐字准确性仍需要核查。** 今天提取出了库存、盘点、备料、采购、主计划与车间小计划、零件和组件齐套、计件工资、扫码报工及人员能力等主要主题，时间戳也方便回查。

实际限制如下：

- 原始稿仍有明显错词、重复和断句问题，不能因为整理稿读起来顺畅，就认为每句识别都准确。
- 人名、人数、交期、缩写、专业词和含糊句子，应回查录音或请参与者确认。
- 两套模型一致也不等于已经核实。对照是帮助找问题，不是自动证明正确。
- 今天试过自动说话人聚类，但产生了过多声纹簇，不能可靠对应真实人数或姓名，交付原稿因此按时间分段保存。后续不默认把这一步的结果用于角色归属。
- TextRank 抽取的是原句，会带上原始识别错误和口语，也不能自动区分现状、面试者观察和未实施建议。

本次没有完成整段录音的逐字听校，也没有带标准答案的准确率测量，因此不记录一个未经验证的“识别准确率百分比”。

## 后续复用步骤

1. 先读取本笔记，确认用户提供的录音、实际活动日期、人物和交付范围。
2. 检查本机已有模型与依赖，能复用就直接使用。旧缓存不存在时，再按项目及模型来源补齐。
3. 为新事项设置独立输入、缓存和输出位置，调整今天脚本中的固定路径、录音名及日期，然后运行识别与抽取。
4. 保留完整识别 JSON、带时间戳的文字稿和必要的独立识别对照。不要用抽取摘要代替全文。
5. 保留听辨待核处；说话人未确认时按时间分段，或明确标为身份待核。
6. 原始稿和总结作为附件归档，日志按 `obsidian-journal` 的规则编写；同一天不同事项分篇。

用户偏好是用开源项目完成声音转文字和原句抽取。现状分析仍需要阅读文字，不能把这套流程说成整项工作完全不使用对话模型或不消耗任何 token。
