# ZigBee RFID 教室考勤系统软件架构（本地先可靠保存，云端异步补传）

> 设计基线：一套 CC2530 代码构建两种设备角色；终端负责采集，协调器负责权威名册和持久化，ESP‑12F 负责网络转发。屏幕提示必须对应真实保存状态。

## 核心概念

- ==“读到卡”“本地已保存”“云端已入库”是三个不同状态==，界面与蜂鸣器不能提前报最终成功。
- ==协调器是本地权威存储点==：短时断网不应阻止考勤，恢复后按事件 ID 幂等补传。
- ==硬件清单先于驱动实现==：题目要求与原理图器件不一致时，必须先决定遵从验收要求还是现有板卡。
- ==CC2530 RAM 紧张==：使用紧凑二进制 ZigBee/串口帧，避免整班大数组和大 JSON 缓冲；JSON 交给 ESP 侧构造。

## 一、需求与现有原理图的差异

本次附带的三页原理图（V1.0，2026-09-17）和对话中提到的硬件应逐项确认：

| 需求描述 | 原理图标注/现状 | 实施前动作 |
|---|---|---|
| RTC：DS1302 | U3 标为 RX8010SJ（I²C） | 若验收指定 DS1302，要改硬件和驱动；不能只换驱动名称 |
| EEPROM：AT24C1024 | U2 标为 AT24C02 | AT24C02 容量仅 2 Kbit（256 B）；需保存大量记录时应扩容。AT24C1024B 的 131072 B 是 128 KiB，不是 1 MB |
| 两个读卡器 | 一台终端＋一台也能读卡的协调器 | 共用同一考勤业务服务，避免两套规则 |
| 中文 OLED | 四线接口，但控制器/分辨率未在原理图注明 | 核实实物型号、I²C/SPI、地址、分辨率和字库 |
| ESP‑12F MQTT | 可做网关，但无密码/网络配置细节 | 将 Broker、Topic、凭据放配置，不写死在共享笔记或源代码 |

器件容量和通信方式以具体厂商料号数据手册为准；板卡原理图优先于对话中的推测。

## 二、节点职责

### 2.1 读卡终端 T01

- 读取完整 UID；按同步的名册版本查身份，或把 UID 原样交给协调器判定。
- 通过 ZigBee 发送刷卡事件，接收时间、名册和保存结果。
- OLED 显示姓名/学号/时间/状态；蜂鸣器区分保存成功、未知卡和失败；按键/LED 提供本地操作及状态。
- 终端没有可靠网络时，只能显示“待传/暂存”；除非事件已写入本地非易失存储，不得宣称已保存。

### 2.2 协调器 C01

- 建网并管理终端；本地读卡也进入同一 `AttendanceService`。
- 维护权威 UID 名册、RTC 时间、考勤记录、待上传队列和状态页。
- 收到事件后校验、去重、写 EEPROM 并读回校验，再向终端回 `STORED_ACK`。
- 通过 ESP‑12F 异步上传 MQTT；网络故障不阻断本地记录。
- 串口命令按学号查询记录、绑定卡、查看空间和联网状态；避免在串口打印中阻塞 ZigBee 事件。

```text
终端读卡 ──ZigBee──┐
                   ├─> 协调器业务服务 ─> EEPROM ─> ESP‑12F ─MQTT─> 服务端
协调器本地读卡 ────┘             └─> OLED / 蜂鸣器 / 串口
```

## 三、资源与软件分层

建议采用分层，但目录名服从现有 IAR/Z‑Stack 工程，不先大规模重构：

```text
App：角色选择、OSAL 事件分发、启动状态
Services：Card / Roster / Time / Attendance / RecordStore / Sync
Transport：ZigBee 业务帧、ESP UART 帧、CH340 CLI
UI：OLED 页面与按键状态机
Drivers：RC522、RTC、EEPROM、OLED、LED、蜂鸣器
Board/Bus：GPIO、软件 SPI、软件 I²C、UART、管脚定义
```

对话中根据原理图指出的资源冲突：CC2530 的 USART1 管脚映射会在 RC522 SPI 所用端口与 ESP UART 所用端口之间发生复用冲突。推荐先核对芯片手册、最终网表和现有代码；可采用 `USART0 → CH340`、`USART1 → ESP`、`RC522 → GPIO 软件 SPI`，但不得在没核实 pin map 前照抄。两种固件可由 `GC_READER_ENDDEVICE` / `GC_READER_COORDINATOR` 编译配置生成，保持驱动同源。

CC2530 RAM 只有 8 KB 量级且需给协议栈留空间。优先使用固定长度结构、有限队列、分页查询和 OLED 局部刷新；网络 JSON 在 ESP 侧生成。队列容量、刷新周期和持久化格式都要经实际工程资源测量后定值。

## 四、可靠考勤数据流

```text
读 UID
 → 记录采集时间和来源设备
 → 建立唯一 event_id
 → ZigBee 发送
 → 协调器校验/查名册/去重
 → EEPROM 写入并读回验证
 → STORED_ACK
 → 终端显示“本地已保存”并响成功音
 → ESP/MQTT 异步上传
 → 服务端数据库提交
 → EVENT_ACK
```

| 状态 | 显示/提示 | 可否响最终成功音 |
|---|---|---|
| UID 已读，业务处理中 | 正在识别 | 否 |
| 已发 ZigBee，等待协调器 | 正在保存 | 否 |
| 仅终端 RAM 暂存 | 待传（重启可能丢失） | 否 |
| 协调器 EEPROM 已提交并验证 | 本地已保存 / 云端待传 | 是 |
| 服务端确认数据库提交 | 已同步到云端 | 可用独立状态提示 |
| EEPROM 满/写入失败/无确认 | 保存失败 | 绝不能响成功音 |

### 4.1 去重与事件 ID

对话中的建议格式：

```text
event_id = 设备 IEEE 地址 + 持久化启动代数 + 本次启动刷卡序号
```

事件重传沿用原 ID；协调器和服务端以此幂等，避免重复计数。启动代数需可靠持久化并考虑 EEPROM 擦写寿命；序号需定义回绕行为。不要只用“学号＋秒级时间”，它不能可靠区分同秒事件、校时和重传。

### 4.2 身份与重复刷卡

- 学号用固定长度 12 位**字符串**保存，保留前导零。
- 名册映射为 `UID → 学号字符串 → 姓名/班级/状态`；新卡读到 UID 但未登记，走受控绑定流程。
- 定义卡片持续停留去抖、重复刷卡时间窗、迟到规则、异常时间和未知卡策略；不要让读卡轮询每次都生成新事件。

## 五、硬件接口与驱动实施前核对

1. 以原理图导出的最终网络表核对 RC522 的 CS/SCK/MOSI/MISO/RST/IRQ、OLED I²C、ESP UART 和 CH340 UART。
2. **RC522 与 ESP 是否争用同一个 USART 映射要先查 CC2530 手册**；若采用软件 SPI，写最小读版本寄存器测试后再接考勤业务。
3. RTC 驱动按实际芯片选择：RX8010SJ 为 I²C 路线，DS1302 是独立三线串行接口，二者不可互换。
4. EEPROM 驱动先核对容量、页大小、写周期、地址引脚、ACK 轮询和写保护脚；分页读回校验后才允许 ACK。
5. OLED 型号与控制器未知时，先做总线扫描/地址确认，再实现页面。中文只带所需字库。
6. 上电先验证电源与 CC2530 烧录，再逐个接入 RC522、OLED/RTC/EEPROM、ESP，避免多故障混测。

## 六、分阶段验收

1. **硬件冻结**：确认最终原理图、网表、RTC/EEPROM/OLED 料号、UART/SPI 引脚复用。
2. **单板最小测试**：CC2530 烧录；RC522 读取版本寄存器和 UID；RTC 走时；EEPROM 写读校验；OLED 可显示。
3. **单终端考勤**：两张以上已绑定卡，未知卡处理、重复刷卡抑制和本地反馈。
4. **ZigBee 双节点**：终端发送、协调器 ACK；断链、重连、重发不丢不重。
5. **持久化**：掉电恢复记录、名册版本、EEPROM 空间耗尽和写失败流程。
6. **ESP/MQTT**：先有网后离线再恢复；验证事件 ID 幂等及服务端 ACK；不要把无密码 Broker 信息硬编码进可公开的知识库。
7. **系统验收**：串口按学号分页查询；OLED/蜂鸣器状态与存储真实结果一致；测量 RAM、栈、队列和掉电恢复。
